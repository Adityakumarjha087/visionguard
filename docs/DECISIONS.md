# Engineering decisions & scope notes

Each entry: decision, why, and what was traded away.

## Architecture

1. **Rule engine lives in the inference service, not the API.** Rules such as "vehicle stops > 2 min"
   or "worker without helmet" need per-track history (positions, helmet sightings) at frame rate.
   Shipping every frame's tracks to Go just to evaluate them would double the hot path. The API owns
   rule *definitions*; it publishes a desired-state document (`vg:config`) and the inference
   service hot-reloads it without restarting the capture pipeline.
2. **Redis Streams with two delivery semantics.** `vg:events` (alerts, stats, crossings, clip and
   description updates) is consumed with a consumer group + `XACK` for at-least-once delivery and
   idempotent handlers (incident ids are generated by the producer, inserts use `ON CONFLICT DO
   NOTHING`). `vg:frames` is tailed with plain `XREAD $` and capped with `MAXLEN ~` — live overlay data
   is worthless if late, so it is never replayed.
3. **Desired state instead of RPC.** The API never calls the inference service to start/stop cameras.
   It writes a versioned document; inference reconciles every second. A restarted inference
   service, API or Redis converges automatically (the API republishes every 30 s).
4. **TimescaleDB for time series.** `detection_counts`, `track_points`, `line_crossings` are
   hypertables with retention policies (30 / 7 / 90 days) and a per-minute continuous aggregate.
   Analytics use `time_bucket` and a `width_bucket` heatmap computed in SQL. Hypertables have no
   foreign keys (write-rate); camera deletion purges them in the same transaction.

## Deviations from the spec (and why)

| Spec | Built | Reason |
|---|---|---|
| Socket.IO client | Native WebSocket with a typed `{type, data}` envelope, reconnect + ping in the client | Go Socket.IO servers lag the v4 protocol; plain WebSocket is simpler and fully tested on both ends |
| WebRTC / HLS.js video | MJPEG over HTTP proxied (and authorised) by the API, boxes drawn on a canvas from WebSocket messages | Sub-second latency without a media server/TURN; HLS adds 2–6 s segment latency. Frames and overlay come from the same processed frame so they stay in sync |
| ByteTrack (library) | Own ByteTrack implementation (Kalman + two-stage IoU association, class-aware) | Avoids pulling Ultralytics/PyTorch into the serving image; fully unit tested |
| YOLO PyTorch in Docker | CPU image ships ONNX Runtime only; PyTorch is an optional extra (`uv sync --extra yolo`) used for export, benchmarks and fine-tuning | Keeps the image free of PyTorch. Measured: ORT CPU EP 46 ms vs PyTorch 34 ms on Apple Silicon (PyTorch wins on CPU), ORT CoreML EP 22 ms; one ONNX file serves CPU/CoreML/CUDA |
| PPE helmet detection with YOLO | Demo uses the deterministic `color-synthetic` detector on generated footage; `scripts/train_ppe.py` fine-tunes YOLO11n on a PPE dataset (synthetic by default, any YOLO-format dataset via `--data`) | Real PPE weights cannot be committed; tests must not download weights |
| GPU metrics | `vg_gpu_utilization_percent` via NVML when present, `NaN` otherwise; GPU compose profile provided | Developed on Apple Silicon — the GPU profile is **untested** |
| Email / Telegram | Implemented (SMTP + Bot API) but disabled unless configured | No real notifications are sent in dev/CI; channels are tested with stubs / `httptest` |
| Multi-tenancy | Single organisation, role-based (admin/operator/viewer); every authenticated user sees all cameras/incidents | Per-camera ACLs were out of scope; IDOR protections cover cross-camera references (a rule can only use zones of its own camera) |

## Real-model honesty

* The mAP shown for `yolo11n`/`yolo11n-onnx` is the **published** COCO val2017 figure (39.5 mAP50-95);
  latency/FPS are **measured** on this machine. The `color-synthetic` mAP is measured on a held-out
  split of the synthetic scenes with exact ground truth.
* Generic COCO YOLO does not know "helmet"; the `missing_ppe` rule needs a PPE model
  (`ppe-yolo11n-onnx`) or the synthetic demo detector.

## Security

* Access JWT (HS256, 15 min, issuer + `typ` checked, `alg` pinned) + opaque refresh tokens stored
  as SHA-256 hashes, rotated on every use; replay of a rotated token revokes all of the user's sessions.
* `?access_token=` is accepted only on GET media/stream/WebSocket routes (browsers cannot set headers there).
* File sources are confined to the video directory (path traversal rejected on both API and inference
  side); RTSP credentials are redacted from logs/status; uploads are size- and extension-limited.
* Per-IP token-bucket rate limits (general and a stricter auth bucket); CORS allow-list; security
  headers; non-root containers; `VG_JWT_SECRET` mandatory in production.
